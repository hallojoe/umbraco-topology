# Optional Azure Blob media with local Azurite

Use this reference when the user requests Blob media, or when converting a project already using Azure Blob storage. Keep the media choice independent of the distributed cache choice. For a new project, select `Umbraco.StorageProviders.AzureBlob` compatible with the project's exact CMS major; include `Umbraco.StorageProviders.AzureBlob.ImageSharp` when the site's image pipeline uses ImageSharp. Verify the registration and configuration API against that provider version. The provider's documented registration uses `AddAzureBlobMediaFileSystem()` and, for the image cache, `AddAzureBlobImageSharpCache()`. Configure one media container shared by CM, both Subscribers, and Single when used; create it idempotently before Umbraco starts, since the provider expects it to exist. Configure the image cache as required by the selected provider. Omit `Umbraco__CMS__Global__UmbracoMediaPhysicalRootPath` from Blob launch profiles; it is required for this skill's shared-disk media mode, not Blob mode.

For local development, add Aspire's Azure Storage hosting integration at the AppHost's existing Aspire version. Model Azure Storage with `RunAsEmulator` so Aspire starts Azurite through the chosen container runtime, add a Blob resource, and reference it from CM, both Subscribers, and Single when Single runs. Wire the provider's expected connection string and container name from the Aspire resource into development configuration without tracked account keys. Ensure the Blob endpoint is reachable by each process; URL generation and image caching must work from the browser-facing CM/CD addresses, not just inside the AppHost. Keep Azurite data persistent across restarts if the SQL database is persistent, so media records do not outlive their files.

On conversion, inspect the existing media provider, settings, and image cache before editing. Preserve a working Blob provider and its storage account; do not substitute Azurite for a live storage account without an explicit local-development choice. If the user requests a switch from disk, do not silently move or discard existing media. Agree on a migration or retain the existing media until it is copied and verified. Apply local emulator settings only to the local topology.

When the runtime is available, upload a valid image on CM and verify its media record and original URL on both Subscribers after restart. Umbraco signs image transformation queries with its imaging HMAC key: appending an unsigned `?width=...` can return HTTP 400 even when Blob media works. Generate a transformed URL through Umbraco's image URL generator or a site's existing crop helper, then request that signed URL on both Subscribers. Confirm the same imaging key is effective on each instance. Document the selected provider, emulator resource, persistence, and local URL behavior.

If a smoke image is created only for local verification, compare the uSync snapshot before and after the run. uSync can export its media record even when the Blob bytes exist only in an ignored local Azurite volume. Remove or ignore that smoke-only export before handing over a fresh-checkout starter; otherwise the snapshot may import a media record whose file is absent. Preserve intentional media assets and existing exports on conversion.
